# lingfeng-workbench 精简设计

状态：当前认可的产品边界与方向  
适用基线：v0.1 救援 MVP；2026-08-19  
详细但未接受的历史产品化草案：[Draft PR #1](https://github.com/lingfeng-xiao/lingfeng-workbench/pull/1)

本文只回答“产品是什么、数据放在哪里、三个部分如何分工”。它不承诺完整 v0.2 的对象数量、页面范围、数据库厂商或实施顺序。

## 产品目标

lingfeng-workbench 让用户从 Hermes 发起、控制和查看工作，并让指定电脑上的 agent runtime 真正执行。系统优先提供一条可审计、可停止、结果留在本机的闭环，而不是把公司电脑变成开发服务器或把本地工作内容集中上传。

## 不变原则

1. Hermes 就是统一用户入口和控制面，不另外建模“主人格”。
2. 服务端只保存控制面所需的最小数据。
3. 文档、代码、日志、报告、凭证、Runtime 原始对话和事件留在对应电脑。
4. 不同电脑的工作区、上下文、任务和 Runtime Session 完全独立，不迁移、不跨电脑同步。
5. 对接对象是 agent runtime，不绑定 WS。WS 是当前实现，未来可以接 Claude Code、Codex 或其它 runtime。
6. 协议按能力描述 runtime，不把某个工具的命令或会话格式写进核心业务模型。
7. Kanban 不属于目标设计，也不作为过渡方案、降级方案或长期需求池。
8. GitHub main 是公开、可恢复的可信设计与源码；Issue 和 Draft PR 只承载提案与历史。
9. 只维护一个个人生产环境。开发环境使用 Codex Cloud 或短期隔离环境，用完可销毁。
10. 不迁移 lf-workbench 或 xlf 的历史数据。

## 三个产品部分

### Hermes 端

Hermes 是对话入口和控制中枢，负责：

- 接收用户意图并创建短任务合同；
- 选择明确的 Node 和本地工作区引用；
- 展示短进度、短结果和待处理交互；
- 对审批做唯一、不可歧义的绑定；
- 保存最小控制状态与审计记录；
- 在风险或信息不足时停止，而不是猜测或自动重放。

Hermes 不保存完整产物，也不复制 Runtime 原始对话。

### workbench-node 与 agent runtime

workbench-node 部署在每台执行电脑上，是该电脑的受控执行代理和 runtime 宿主。它负责：

- 只领取明确指向本 Node 的任务；
- 把任务交给本机的 WS、Claude Code、Codex 等 runtime；
- 约束允许的工作区和副作用；
- 回传短进度、交互请求和短终态；
- 把完整结果、日志和 Runtime 对话保存在本机；
- 在断线、歧义或合同不匹配时安全失败。

Node 不是跨电脑调度器。一个 Node 的任务和上下文不能迁移到另一个 Node。

### Sites 网页端 workbench

Sites 将来承载结构化页面，面向不适合在对话里完成的查看和管理：

- 需求与任务的结构化视图；
- Node、Run、Interaction 的当前状态；
- 当前有效证据和冻结边界；
- workbench 自身的设计、开发和演进记录。

页面读取的仍是最小控制数据，不展示或集中存储电脑上的完整代码、日志、报告和 Runtime 对话。Sites 不是当前 MVP-A 的必经链路；其机器身份、数据库接入和正式页面尚未形成已接受实现。

## 当前已验证链路

当前救援拓扑是：

Hermes Plugin → 受限 SSH worker-stream → 办公电脑 workbench-node → WS

回程只带控制事件、短进度、交互摘要和短结果；完整结果留在办公电脑。MVP-A 已用真实 WS 跑通。MVP-B 的批准后恢复尚未跑通，具体证据见 [当前状态](current-state.md)。

当前源码仍包含 Kanban 适配，这是 v0.1 的历史实现细节，不改变“目标设计没有 Kanban”的决定。

## 目标方向

长期方向包含四类职责，但本次不要求立即拆仓库或拆服务：

- GitHub：可信设计、源码、变更提案和可审计版本。
- Hermes：统一入口、用户决策和控制面。
- Sites Web：结构化查看与管理页面。
- 每台电脑的 workbench-node + agent runtime：本地执行与本地产物。

组件之间只交换短合同和短状态。将来可以独立开发与验证每个边界，但具体仓库结构、API、数据库和部署拓扑需要另行做小型设计，不从历史 v0.2 草案自动继承。

## 数据边界

服务端允许保存的最小信息包括：

- WorkItem、Mission、Run、Interaction、Node 的标识与关联；
- 目标、验收、风险和授权范围的短摘要；
- 进度、终态和结果短摘要；
- 幂等、时间戳、Gate 与必要审计信息。

默认不得离开执行电脑的内容包括：

- 源码、文档正文和业务数据；
- 完整日志、完整报告和构建产物；
- 凭证、Cookie、Token、环境变量和密钥；
- Runtime 原始对话、工具事件和详细推理上下文。

目前不做自动数据脱敏，因此边界必须由产品合同、工作区限制和执行流程明确保证。公开 GitHub 可能被公司网络审计，禁止提交公司材料或秘密。

## 开发与发布边界

- workbench 的源码开发、测试和候选生成在 Codex Cloud 或其它个人隔离环境完成。
- 公司电脑只拉取经过 Gate 的明确版本，并承担本地运行或真实验收；不在公司电脑编写、提交或推送 workbench 源码。
- 分支、PR、测试通过都不自动等于可合并或可发布。
- 合并、部署、权限变化和生产写入分别需要对应的明确授权。
- 设计必须先进入 GitHub main，才能作为新电脑继续开发时的默认依据。

## 当前不作决定

本精简设计不决定：

- 是否拆成多个仓库或多个服务；
- 数据库厂商和免费额度方案；
- Sites 的机器身份与网络路径；
- 完整页面信息架构；
- 全量对象模型和 52 项路线图；
- 多电脑同步、任务迁移或历史数据导入；
- 自动升级、回滚、Archive/GC 和生产恢复。

这些问题保留到基础闭环稳定后，以独立提案逐项确认。
