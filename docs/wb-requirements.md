### WB-002 恢复纯净源码包
- 业务描述：将允许范围内的运行时源码与构建元数据恢复为可审查仓库基线。

- 风险：遗漏源码或夹带运行数据。
- 回滚边界：回到恢复前空仓库；不影响服务器部署副本。
- 初始状态：已证。

### WB-003 敏感信息与数据边界检查

## P3 产品合同

### WB-301 冻结顶层空间
- 业务描述：冻结产品只有“我的工作”和“Workbench”两个顶层隔离空间，Hermes 仍是统一入口和控制面。
- 可验证 AC：
  - 顶层导航、路由、权限和数据归属只存在“我的工作”与“Workbench”两个空间。
  - “我的工作”承载用户 WorkItem、运行、审批、Node/Runtime 与产物引用。
  - “Workbench”承载产品能力、Observation、Proposal、Decision 与 Release，不成为独立人格。
  - 两空间默认隔离；跨空间引用必须显式、最小且可追溯，不能隐式复制上下文。
  - 不新增 Kanban、第三顶层空间或另一套人格入口。
- 依赖：无。
- 最低证据：信息架构、路由/权限矩阵、跨空间负向测试。
- 风险：空间边界漂移、Workbench 自我授权或用户上下文被复制。
- 回滚边界：回退新增空间/入口；不保留 Kanban 或第三空间兼容。
- 初始状态：缺失。

### WB-302 业务空间核心对象
- 业务描述：定义“我的工作”中的 WorkItem、Mission、Run、Interaction、Node、AgentRuntime、ArtifactReference、ControlEvent。
- 可验证 AC：对象归属、唯一 ID、生命周期和关系明确；八类对象均能 round-trip；ArtifactReference 只引用已分类产物；ControlEvent 保留审计顺序；不含 Kanban/TaskRepository 长期边界。
- 依赖：301。
- 最低证据：领域合同、schema 与 API 契约测试。
- 风险：旧 Kanban 标识继续成为核心依赖。
- 回滚边界：回退新 schema/API；不迁移旧 lf-workbench/xlf 数据。
- 初始状态：矛盾。

### WB-303 Workbench 产品空间核心对象
- 业务描述：定义 Workbench 产品空间中的 ProductArea、Capability、Proposal、Release、Observation、Decision，并与个人工作隔离。
- 可验证 AC：六类对象均有稳定 ID、关系和生命周期；Observation 只能形成 Proposal 草稿；Decision 记录用户决定；Proposal 默认无授权；Release 不能因 Proposal 接受或 PR 合并自动生产发布。
- 依赖：301。
- 最低证据：对象/权限矩阵、Gate 契约与负向测试。
- 风险：Workbench 自我授权或跨空间读写。
- 回滚边界：停用 Workbench 写入口，不影响“我的工作”。
- 初始状态：缺失。

### WB-304 状态机与人工 Gate
- 业务描述：让运行、审批、Proposal 和发布的每次状态变化可解释、可拒绝。
- 可验证 AC：
  - 合法转换、终态和失败/uncertain 语义明确；重放、越级和过期请求被拒绝。
  - 硬 Gate 1：用户决定某个精确 Proposal 是否接受；未接受不得进入获准实现状态。
  - 硬 Gate 2：用户决定某个精确 Release/commit/saved version 是否生产发布；Proposal 接受或 PR 合并不能替代。
  - 硬 Gate 3：破坏性数据库迁移、权限扩大或数据边界变化发生前，必须针对精确变更再次单独确认。
  - 设计 Gate 可作为前置，PR 合并可作为额外治理 Gate，但二者都不能替代上述三类硬 Gate。
  - 每个 Gate 绑定对象、版本、范围、决定者和时间；决定重放不产生第二次授权。
- 依赖：302、303。
- 最低证据：状态图、转换表、正负契约测试。
- 风险：重复审批、越级发布、终态复活。
- 回滚边界：状态事件只追加补偿，不改写审计历史。
- 初始状态：不完整。

### WB-305 Artifact 数据分类
- 业务描述：每个产物先分类，再决定留在本地或进入 R2。

### WB-401 审批投递确认
- 业务描述：审批结果只有在目标 Node 明确确认接收后才标记已投递。

  - ACK 重复或延迟到达只返回既有结果，不回退后续状态。
  - 重复 ACK 的业务推进、执行、副作用以及重复推进/执行计数均为 0；只允许增加幂等命中审计。

### WB-402 Node Outbox
- 业务描述：Node 离线或发送失败时保留待发 control 事件并安全重试。
- 可验证 AC：
  - control 事件先以稳定 message/idempotency ID 持久化，再尝试发送。
  - 未 ACK 项在进程崩溃或系统重启后仍可恢复，ACK 后才删除或转为可审计完成记录。
  - Outbox 设明确条目容量、字节上限和积压告警；达到上限时采用可观察的拒绝/背压，不静默丢弃未确认项。
  - 重试保持同一 ID；重复 ACK、乱序 ACK 和延迟 ACK 不删除错误项。
  - 相同目标按持久化 sequence 确定性发送；重启后顺序不变，不因失败项无限阻塞可独立处理的其他目标。
  - 满容量、永久失败和超过重试预算均进入明确错误状态；积压不可无界增长且必须可人工处置。
  - 队列只含最小 control 数据；local-only 正文、secret 和完整日志不得入队上云。
- 依赖：405。
- 最低证据：本地持久化、崩溃恢复和边界测试。
- 风险：事件丢失、无限重放或泄露本地内容。
- 回滚边界：保留可导出的本地队列；协议版本可回退。
- 初始状态：缺失。

### WB-403 Node 自动重连

- 业务描述：公司电脑只下载、验证和安装，不开发、不构建、不 push。
- 可验证 AC：
  - 公司电脑的 Workbench 本地仓库无 remote，Node 不持有 GitHub 读写、Sites、D1、R2 凭证。
  - 升级包只从 Hermes 正式通道获取，不从开发分支、PR artifact 或任意 URL 获取。
  - 安装前完成 602 的全部校验；失败时不覆盖当前可运行版本。
  - 升级过程不 checkout 源码、不构建、不测试源码、不 commit、不 push。
  - 安装记录来源 Release、版本、hash、签名验证结果、时间和目标 Node，不记录 secret。
- 依赖：603。
- 最低证据：权限/网络检查和一次隔离升级演练；当前仅直接回读公司电脑本地仓库没有 remote。
- 风险：办公机获得开发凭证或绕过 Gate。
- 回滚边界：停止升级通道，维持当前已验证版本。
- 初始状态：不完整。

### WB-605 Node 双版本回滚
- 业务描述：Node 保留当前与上一已知良好版本，失败时快速回退。
- 可验证 AC：
  - Node 明确保留 current 与 previous 两个已验证版本及其 manifest/验证记录。
  - 安装和版本指针切换原子化；任一时刻只有一个版本提供服务。
  - 新版本安装失败、启动失败或健康检查失败时可回到 previous。
  - 用户可显式选择已验证 previous 回滚；未知或未验证包不可成为回滚目标。
  - 回滚不迁移、不合并、不上传本地上下文，也不改写 D1 业务历史。
  - 回滚失败时停在最后可确认状态并暂停新任务，不并发启动双版本。
- 依赖：604。
- 最低证据：安装失败、启动失败、人工回滚演练。
- 风险：两个版本同时运行或状态格式不兼容。
- 回滚边界：仅切 Node 程序版本，不改 D1 历史和本地工作区内容。
- 初始状态：缺失。

### WB-606 Sites 发布流程
- 业务描述：在 GitHub/CI 与 Gate 0 基础上，经用户 Release Gate 发布唯一 Sites 项目。
- 可验证 AC：
  - 只对唯一 Lingfeng Workbench Site 创建 saved version，不创建第二套长期 Workbench 环境。
  - saved version 绑定已合并 commit、云 CI run、构建产物和设计/实现范围。
  - merge main 不自动部署；用户必须明确批准精确 commit 与精确 saved version，Proposal 接受或 PR 合并不能替代。
  - 发布前建立可回读的 D1 快照或等价恢复点；若平台只支持逻辑导出，必须先满足 206 的真实恢复验收，不能用 dry-run 代替。
  - 发布记录同时保存 PR、commit、Sites saved/deployment version、schema version 和回滚点。
  - Agent、Node 和仓库均不持有可复用生产密钥；部署通过受控平台调用面完成。
  - 部署后进入明确观察窗口，回读版本、身份、health/work-items、静态资源、Worker events 和错误；失败不覆盖最后已知良好版本。
  - 支持通过 Sites 外部控制面回滚，不依赖当前故障应用自身的管理 API。
  - custom/private 身份 Gate 未通过时不得以成功部署记录宣告 Gate 0 或路由健康。
- 依赖：102～105、201～208。
- 最低证据：发布记录、Gate、部署版本和回滚点；当前仅 v3 saved version deployment succeeded，尚无 GitHub/CI/Gate/回滚追溯。
- 风险：未批准部署或版本与源码不一致。
- 回滚边界：切回上一 Sites 版本；数据恢复独立处理。
- 初始状态：不完整。

## P7 验收与收口

### WB-701 云端开发链验收
- 业务描述：证明从需求到 PR 的开发全程只在云端，main 受保护。
- 可验证 AC：
  - 从用户批准需求开始，云任务基于指定 main commit 创建隔离分支。
  - 代码/文档修改、构建、测试和评审全部在 Codex Cloud/云 CI 完成。
  - PR 可追溯到需求、分支、commit、CI run、评审和用户 Gate。
  - 失败检查或缺少必要评审时不能合并；若套餐无法强制保护，验收明确失败而非用流程冒充。
  - 公司电脑仓库无 remote，不承担开发、构建、测试或 push。
  - main、恢复首 commit 和恢复 tag 在验收前后保持预期不变。
- 依赖：101～105。
- 最低证据：端到端 PR 记录和权限负向验证；当前 cloud task→分支→Draft PR 与办公仓库无 remote 只覆盖部分链路。
- 风险：隐藏的本地构建或管理员绕过。
- 回滚边界：不合并验收分支，撤销临时权限。
- 初始状态：不完整。

### WB-702 断线与重启验收
- 业务描述：证明网络和进程故障不会丢事件或重复执行。
- 可验证 AC：
  - 按原合同逐项、独立执行并留证以下七种场景：
    1. Node 派发前断线。
    2. 派发后未 ACK 断线。
    3. 审批回答后断线。
    4. Node 重启。
    5. Hermes 重启。
    6. 重复事件。
    7. 长时间离线后恢复。
  - 上述每一个场景都必须逐项证明：
    - 不丢审批。
    - 不重复执行。
    - 不误重放未知副作用；副作用无法确认时进入 `uncertain`，不得猜测完成或失败。
    - 最终 Run、Interaction 与投递状态一致。
    - Outbox 最终清空或进入明确、可观察、可处理的错误状态。
    - 启动对账结果可解释、可审计，且不包含 local-only 正文。
  - 七种场景均不要求 Node 直连 Sites/D1/R2，也不迁移电脑上下文。
- 依赖：401～405、407。
- 最低证据：故障注入、Outbox 与最终状态对比。
- 风险：只覆盖理想重连路径。
- 回滚边界：暂停派发并回退 Node/应用版本。
- 初始状态：缺失。

### WB-703 审批验收
- 业务描述：证明审批唯一绑定、可重投、可过期且不误批。
- 可验证 AC：
  - 审批矩阵覆盖零个、一个、多个待审批项以及显式正确/错误 Interaction ID。
  - 多审批时裸 `/lf y`、`/lf n`、`/lf s` 全部拒绝；唯一审批时回显唯一 ID。
  - 覆盖决定重复、ACK 丢失、ACK 重复、乱序、延迟、过期、取消及列表后集合变化。
  - ACK 前不得标记 delivered；重投使用同一投递幂等 ID。
  - 同 ID 冲突决定被拒绝，终态不被旧消息复活。
  - 全部使用隔离合成审批，不重复原任务真实 `/lf y` 最终验收。
- 依赖：401、407、408、504、701。
- 最低证据：合成审批矩阵和投递确认记录。
- 风险：用单一真实成功案例替代边界测试。
- 回滚边界：关闭极简和页面写入口，保留显式 ID 流程。
- 初始状态：缺失。

### WB-704 数据边界验收
- 业务描述：证明四类数据按声明进入正确位置，未声明默认留本地。
- 可验证 AC：
  - 扫描所有云存储面：GitHub 源码/历史/Release、云 CI 日志与产物、Sites 配置/日志/事件、D1、R2。
  - control 只出现在允许的业务字段；cloud-safe 产物都有分类声明、来源、hash 和授权 Gate。
  - local-only、未声明内容和完整办公上下文不出现在任何云存储面。
  - secret 不出现在仓库、D1、R2、Release、构建产物或日志；专用秘密存储只核对引用和权限，不回显值。
  - Node 无 GitHub/Sites/D1/R2 凭证，且网络负向检查证明不能直连云数据面。
  - 发现误传时验证隔离、撤销引用和 secret 轮换边界，不依赖自动脱敏。
- 依赖：003、104、202、305、601。
- 最低证据：分类正负测试、权限和网络检查。
- 风险：测试样本未覆盖真实办公内容形态。
- 回滚边界：关闭上传并隔离误传对象，按事件响应处理 secret。
- 初始状态：缺失。

### WB-705 备份恢复验收
- 业务描述：证明 D1 control 数据可逻辑恢复且 R2 引用一致。

- 回滚边界：回到演练前恢复点，不影响在线事实源。
- 初始状态：缺失。

### WB-706 应用和 Node 回滚验收
- 业务描述：分别证明 Sites 应用与 Node 可以回到已知良好版本且互不误伤数据。
- 可验证 AC：
  - Sites 从当前版本回到上一已知良好 saved version，回读身份、健康、路由和版本。
  - Sites 回滚前后 D1 业务历史与 R2 对象不被覆盖或隐式恢复。
  - Node 从 current 回到 previous，校验签名/manifest、单版本运行和健康状态。
  - Node 回滚不改 GitHub/Release/D1 历史，不迁移或删除 local-only 上下文。
  - 分别覆盖应用失败、Node 安装/启动失败和二者组合不兼容；失败时暂停新任务。
  - 两条回滚链各有前后版本、用户 Gate、时间、结果和返回最后良好组合的记录。

- 最低证据：两条独立回滚演练和前后版本记录。
- 风险：把数据恢复与应用回滚混为一谈。
- 回滚边界：失败即停在最后已知良好组合并暂停派发。
- 初始状态：缺失。

### WB-707 发布追溯验收
- 业务描述：从运行中的版本反查用户 Gate、Release、签名包、CI 和源码 commit。

  - tag、资产、hash、签名、版本或 Gate 任一不一致/断链时，不允许标记已发布或继续分发。

- 初始状态：缺失。
