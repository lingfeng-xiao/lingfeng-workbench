## 2. 产品定位

Hermes 本身就是统一用户入口和控制面，不另设“主人格”。产品只有两个顶层隔离空间：

1. **我的工作**：用户的需求、任务、运行、审批、节点和产物。
2. **Workbench**：观察产品自身、形成 Proposal 草稿、展示发布追溯；不得自行接受 Proposal、合并 PR 或发布生产版本。

所有越过人工 Gate 的动作都必须由用户明确确认。三个不可替代的硬 Gate 是：Proposal 是否接受；精确 Release 是否生产发布；破坏性数据库迁移、权限扩大或数据边界变化发生前再次单独确认。设计 Gate 可以作为前置，PR 合并可以作为额外治理 Gate，但两者都不能替代任何硬 Gate。

## 3. 不可更改的长期边界

- v0.2 彻底移除 Kanban：无过渡期、无双写、无兼容层、无历史迁移，也不保留 `TaskRepository` 作为长期边界。
- 只有一个长期在线环境。D1 是控制面业务数据唯一事实源；R2 只存明确声明为 cloud-safe 的产物。
- GitHub 公开仓库是源码唯一事实源，只允许 Workbench 源码、适合公开的安全设计/文档和明确发布资产。开发、构建、测试和评审只发生在 Codex Cloud 或云 CI。Workbench 自动化/生产身份仍必须 repo-scoped，只能访问 `lingfeng-workbench`；用户通用 GitHub 插件不属于 Workbench 生产身份，可保持现状。
- 公开仓库与 R2 cloud-safe allowlist 是不同边界；公开不改变唯一 Sites 项目的 custom/private 访问策略，也不改变 D1/R2、Hermes machine identity、数据分类、人工 Gate 或发布链。
- 公司电脑不开发、不构建、不 push；Node 发布包只走“云 CI→正式 GitHub Release→Hermes→Node”，R2 不承担 Node 包分发角色。
- Hermes 是唯一机器网关。办公 Node 不直连 Sites、D1、R2，也不持有相应凭证。
- 不同电脑的本地上下文完全独立；同一 WorkItem 不得换电脑继续，跨电脑继续必须新建独立 WorkItem，且上下文不迁移、不同步。
- 统一对接对象为 `AgentRuntime`；v0.2 仅支持办公电脑和 WS Runtime。
- 数据分为 control、cloud-safe、local-only、secret；未声明的数据一律按 local-only 处理。cloud-safe 采用封闭 allowlist，只允许 Workbench 自身设计文档、Workbench 自身测试报告、Workbench 页面截图、合成 Fixture 和用户明确确认安全的导出文件。
- 公司代码及 diff、原始日志/SQL/数据库导出、客户或生产数据、完整业务测试或构建报告、Runtime 原始事件与对话、办公电脑绝对路径及任何未明确分类数据均为 local-only。
- 不做自动脱敏。发送方必须先作分类声明，边界不清即拒绝上传。
- 多个待审批项存在时拒绝裸 `/lf y|n|s`；只有唯一待审批项时才允许极简命令。
- 不迁移 `lf-workbench`/`xlf` 历史数据，不重复原任务的真实 `/lf y` 最终验收。

## 4. v0.1 只作为恢复证据

当前恢复代码中仍可见 Kanban adapter、`TaskRepository`、`kanban_task_id` 和 Hermes 侧 SQLite。这些事实与 v0.2 的目标边界冲突，必须通过后续经批准的实现删除或替换；本设计 PR 不改代码。

当前代码也提供了可继承但必须重新验收的设计线索：版本化消息包络、message id 去重、运行状态、审批状态和 Node 本地状态。当前 slash command 在多审批时会拒绝裸 `y/n`，但仍允许裸 `s`；这与 v0.2 对 `y/n/s` 全部拒绝的决定冲突，不能直接沿用。

## 5. 人工 Gate

| Gate | 性质 | 用户决定 | 通过后允许 | 明确不允许 |
|---|---|---|---|---|
| G0 设计 | 前置治理 Gate | 接受本组设计文档 | 拆分 Proposal/实现工作包 | 自动开始实现；替代任何硬 Gate |
| G1 Proposal | **硬 Gate** | 是否接受某一精确 Proposal | 进入该 Proposal 明确授权的实现范围 | 自动合并、扩权、改数据边界或生产发布 |
| G2 PR | 额外治理 Gate | 是否合并指定 PR | 形成已合并源码基线 | 替代 Proposal、敏感变更再确认或 Release Gate |
| G3 敏感变更再确认 | **硬 Gate** | 是否允许精确的破坏性数据库迁移、权限扩大或数据边界变化 | 只执行被确认的敏感变更 | 从设计批准、Proposal 接受或 PR 合并继承授权 |
| G4 Release | **硬 Gate** | 是否将精确 commit/package/saved version 生产发布 | GitHub Release 分发或唯一 Sites 项目上线 | 自动部署其他 commit/version；Node 绕过 Hermes 取包 |

任何 Gate 都必须绑定唯一对象 ID、版本或 commit；含糊的“继续”不得扩大授权范围。G0/G2 即使通过，也不能替代 G3；G1/G2 通过也不能替代 G4。

## 6. 本设计的非目标

- 不选择 ORM、前端框架、签名算法、备份频率。
- 不引入或预先指定第三方服务。
- 不修改业务代码、`pyproject.toml`、恢复说明、manifest 或 tag。
- 不部署 Sites，不接触 D1/R2，不连接办公 Node，不执行真实审批验收。
- 不设计历史数据迁移或多环境同步。
